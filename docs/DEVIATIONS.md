# Deviation Log

Every difference between what we built and what the submitted documents (Synopsis, SRS v1.1, SAD v1.0, Test Plan v1.0) say is logged here, so it can be explained at the final demo. Anyone can add a row via a PR; Prithvi maintains the file.

| # | Document & section | What was planned | What we did | Why | Logged |
| --- | --- | --- | --- | --- | --- |
| D-01 | SRS 9.2, Synopsis 10, Test Plan 3 & 12 | Six two-week sprints; features spread over Sprints 1–6 | Two one-week sprints (Sprint 1: 19–23 Oct, Sprint 2: 26–30 Oct) after a dry-run week (13–16 Oct). Sprint 1 = thin end-to-end product (register, login, real-time DM, rooms, persisted history, CI). Sprint 2 = presence, offline delivery, typing, read receipts, room admin/RBAC, security, performance, Docker, docs | Course Part-2 deliverable schedule | 14 Oct |
| D-02 | Test Plan Appendix B (RTM) | Test cases scheduled as "Planned Sprint 3/4/5" | Same tests, re-mapped to Sprint 1 or Sprint 2 (see `docs/RTM.md`) | Follows from D-01 | 14 Oct |
| D-03 | SRS Appendix B (Message entity) | Message fields: message_id, room_id, sender_id, content, timestamp, status | Adds an `idempotencyKey` field (unique per sender) | Needed to implement SAD 3.4.2 (dedup of retried sends); not a behaviour change | 14 Oct |
| D-04 | SRS 3.1 (Chat Dashboard), Synopsis 8.10 | Users find each other through search, and the dashboard lists the user's conversations | Sprint 1: a DM is started by entering the other user's **user ID** (shared via a "Copy my ID" button), and the DM list is kept per user in the browser's `localStorage` (#62) | SAD 3.2 has no user-search or conversation-list endpoint; user search is CS-33 (Sprint 2). Temporary: to be replaced once CS-33 lands | 14 Oct |
| D-05 | SAD 3.2.2 (`message:send` / `message:new`) | `message:send` → `message:new`, `message:status` | Same events, plus: DM `message:new` also carries `kind: 'direct'` and `senderUsername`; `message:send` also answers through a Socket.IO ack `{ ok, message }` / `{ ok: false, error }` (see `docs/INTEGRATION.md` §7) | Additive only. Lets the client list a DM from someone new by name, tell DMs from room messages, and retry a send that got no answer | 14 Oct |
| D-06 | SAD 3.2.2 (`room:create` / `room:join` / `room:leave`) | `room:create` → `room:created`; `room:join` / `room:leave` → `room:memberJoined` / `room:memberLeft` | Same events, plus `room:joined` / `room:left` sent to the requesting socket and a Socket.IO ack `{ ok, ... }` / `{ ok: false, error }` on all three (#66) | Additive only. Confirms the action to the requester even when nothing changed (already a member / not a member) | 14 Oct |
| D-07 | SAD 3.2.2 (room socket events) | A cached room can be rejoined with `room:join` after reconnecting | Adds `room:restore`, which checks the persisted membership and joins only the socket channel; it never creates or recreates membership | Prevents stale browser storage on one device from undoing a leave on another | 15 Oct |
| D-08 | SRS 9.2, Part-2 sprint plan | All backlog items finished within Sprint 1 (19–23 Oct) and Sprint 2 (26–30 Oct) | Unfinished Sprint 1/2 items were completed in an extra **Sprint 3** (9–15 Nov), as the Part-3 brief §3 allows. They keep their original Sprint 1/2 milestone (so the plan stays visible) and carry a `spillover` label; Sprint 3 also holds the Part-3 testing work (#74–#77) | Spill-over from the shortened schedule; Part-3 brief §3 | 11 Nov |
| D-09 | SAD 3.2.2 (socket events) | Events and payloads as listed in SAD 3.2.2 | Additive: `session:ready { userId, username }` after connection setup; `message:read` also answers through an ack; `typing:update` carries `{ conversationId or roomId, userId, username, typing }`; status changes go to all of the sender's tabs; `RATE_LIMITED` is returned on the `message:send` ack. Full list in `docs/API.md` | Lets the client know when the session is ready, show who is typing, and keep several tabs in sync | 11 Nov |
| D-10 | SAD 3.3 (error codes) | One code per failure class | Wrong login credentials return `401 AUTH_INVALID_TOKEN` (the SAD has no separate credentials code); the message is identical for an unknown user and a wrong password | Stays inside the SAD code list and avoids account enumeration | 11 Nov |
| D-11 | SRS App. B (Message.content ≤ 2000), SEC-003 | Content stored as sent, up to 2000 characters | Content is stored **HTML-escaped** (`& < > " '` as entities, control characters removed) and the 2000-character limit applies to the stored form, so text with many special characters is effectively a little shorter. Clients decode the entities and render plain text | Enforces SEC-003 before storage, as the SRS requires, without changing the field size | 11 Nov |
| D-12 | SRS 2.5 / tool stack (bcrypt) | `bcrypt` library | `bcryptjs`: the same bcrypt algorithm and hash format (`$2a$`/`$2b$`), pure JavaScript | Avoids native compilation on Windows and in Docker/CI | 11 Nov |
